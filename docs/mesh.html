Routers

Kwirth Mesh

Some clusters cannot be reached directly: a Kwirth behind NAT, behind a firewall, in a DMZ, on a laptop. Kwirth Mesh reaches them anyway. A router carries Kwirth's traffic to a cluster that has no direct path, and that cluster shows up in your cluster list like any other — tabs, live channels and Magnify included.

What is Kwirth Mesh?

Kwirth Mesh is built from routers, a type of extension of its own. A router lives only in the back end: it has no tab and no panel. You install it from the Routers manager, configure it in its dialog, and it writes what it does in Kwirth's log. Its one job is to carry traffic to a cluster you cannot reach.

The rule of thumb against the other families: a plugin draws something you open, a provider produces data, a DCE provides objects other extensions call. A router carries traffic to a cluster that has no direct path.

A router decides how the traffic travels — a tunnel, a bastion, a proxy, a link between two Kwirths. Kwirth decides who may send it. And the cluster at the other end still decides what you may do there.

How it works

An entry of your cluster list keeps the cluster's real URL — that is its identity, what you see and what is exported — plus a route: which router reaches it, and the target cluster's uid. Everything Kwirth does with that cluster goes to <root>/router/<id>/… of your own Kwirth instead: API calls, live channels, Magnify, the extra WebSockets some channels open.

no restart
Installing, updating and uninstalling a router is hot: one dispatcher serves every router, and a router is up the moment it is installed.
never the real URL
A routed entry whose router is not installed does not connect at all. It never falls back to the real URL — which is precisely the one that cannot be reached.
the other side decides
The API key of a routed entry is the target cluster's. The router carries it untouched and that cluster authenticates and authorizes you with it: a router never gives you more than the target cluster would.
its own configuration
Kwirth's own dialog, drawn from the fields the router declares. Passwords and keys are kept in a Kubernetes Secret, shown masked with an eye to reveal them, and saving applies at once.
its own scopes
A router may declare scopes, and they appear in the security editor next to everybody else's.
status and log
Each router's card says how it is right now — Started, Error or Failed, with the reason — and everything it does goes to Kwirth's log under the Routers component.

Available routers

The first router is the one that proves the type, and it is open source. Routers for other paths — a bastion, a corporate proxy, a hub of many clusters — use the same contract.

🌉

Bridge

Two Kwirths that reach each other through one outbound link. Only one of them needs to reach the other: with that single link, each sees the other in its cluster list, even when one is behind NAT or a firewall. Magnify desktop and a cluster's Kwirth, a lab and the cloud, home and office.

available · open source

Install Bridge in both, give A the URL of B and an access key of B with the scope bridge$peer, and save: A links to B at once, without restarting either. Then each Kwirth adds the other to its cluster list with the route bridge.

Security

Kwirth authenticates everything that goes into a router, before the router sees a byte, and tells the router who is calling. There are exactly three ways in:

a route ticket
Your browser. Kwirth gives your session a ticket and renews it on its own. It travels in the URL (a browser cannot put headers on a WebSocket), Kwirth removes it before the router sees the path, it lasts 10 minutes and it is not your credential: it only says which session is using the route.
loopback
Your Kwirth's own back end, when a plugin connects to a routed cluster from the server. Accepted only from the same machine.
an access key
Another Kwirth or a script, in the Authorization header. What a key may do through a router is the router's decision, usually by a scope it declares.

Deleting an access key cuts at once the router connections made with it and the route tickets it was given. And a router carries traffic authenticated as the user: install routers you trust, as you would plugins.

Build your own router

A router is a small back-end package. Kwirth includes a scaffolder that generates a working one — an echo router that shows every part of the contract — ready to build and install:

node tools/create-kwirth-router.mjs --id my-router --publisher @my-scope
cd routers/my-router && npm install && npm run build
cd dist && npm pack        # install the .tgz from the Routers manager

The contract is IRouter, in @kwirthmagnify/kwirth-common-back:

getRouterData()
Its id, its path template and whether it needs a route ticket.
routerRequest(req, res, caller)
An HTTP request below /router/<id>, already authenticated, without the ticket in the path.
routerWebsocket(ws, req, caller)
A WebSocket below /router/<id>, already authenticated.
getConfigSchema()
The fields of its configuration dialog; the password ones go to the Secret.
getScopeCatalog()
The scopes it declares, for the security editor.
startRouter · applyConfig · stopRouter
Its lifecycle: started with its saved configuration, the configuration applied hot, stopped on uninstall or update.
getStatus()
What its card in the Routers manager says.

caller.via says how Kwirth let the traffic in (ticket, loopback or accesskey), and caller.accessKey is the validated key when there is one. While you develop it, point Kwirth at your build, the same way as any other extension — it reloads the router on every build:

{
  "routers": {
    "my-router": "../routers/my-router/dist"
  }
}

A plugin can be a router too — a channel with a panel of its own that also carries traffic. It implements both contracts and is installed as a plugin: that is a pluter, the same way a plugin that also produces data is a pluvider.
